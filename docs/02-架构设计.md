## 1. 系统上下文

### 1.1 业务背景

采购报价数据分散在几十份 Excel 中，格式、表头位置、字段命名不统一，供应商报价横向扩列，价格/税费/运费混写在备注里。使用者查找历史报价依赖记忆逐文件翻查，效率低且无法追溯。本系统将历史 Excel 集中导入为"物料—需求—供应商—报价—来源"结构化模型，提供统一检索入口，并保证每条结果可回到原文件、工作表、行号核对。

### 1.2 目标与成功指标

| 目标类型 | 指标 | 目标值 | 验证方式 |
|----------|------|--------|----------|
| 业务目标 | 查询成功率 | ≥ 80%（试运行后校准） | 用户行为抽检 |
| 业务目标 | 可追溯率 | 100% | 全量记录来源字段非空校验 |
| 性能目标 | 常用查询 P95 | ≤ 2 秒 | 基准测试 |
| 性能目标 | 1000 行模板解析预览 | ≤ 60 秒 | 样例基准测试 |
| 可靠性目标 | 数据零丢失 | 备份可恢复，批次原子写入 | 恢复演练记录 |
| 运维目标 | 部署/回滚/备份可执行 | 有脚本有手册 | 运维走查 |

### 1.3 文档适用范围与设计对象

- 设计对象: POM 历史采购报价查询系统（Web 应用 + 导入引擎 + 数据存储）
- 设计类型: 新建系统
- 所属版本/阶段: V1.0 MVP（见 docs/01-版本规划.md）
- 当前范围内模块: 账号与权限、Excel 导入、报价查询、数据维护、系统管理（用户/审计/备份状态）
- 明确不在范围内: 采购审批/订单/合同、仓储库存、财务付款、ERP 对接、微信抓取、搜索集群与微服务

### 1.5 干系人与关注点

普通用户
- 角色/团队: 采购/设备/生产岗（5-10 人）
- 关注点: 找得快、看得懂、来源可信
- 成功标准: 常见物料 2 分钟内确认历史报价与来源
- 备注: 移动端也要能查询（V1.1 深度适配）

数据维护员
- 角色/团队: 数据归档责任人
- 关注点: 乱表能导、导入前可控、错了能改
- 成功标准: 三份样例不修改原文件即可导入且可纠错
- 备注: MVP 可由管理员兼任

系统管理员/运维
- 角色/团队: 系统责任人
- 关注点: 账号可控、操作可审计、备份可恢复、部署可回滚
- 成功标准: PRD 9.3 运维/安全/恢复门槛全过
- 备注: 与数据维护员可为同一人但权限模型不合并

业务方
- 角色/团队: 需求与验收方
- 关注点: 不做 ERP、MVP 边界不膨胀
- 成功标准: PRD 第 9 章门槛通过
- 备注: 持供新样本

### 1.6 系统边界

```text
┌────────────────────────────────────────────────────────────────────┐
│                           POM 系统边界                              │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────────────────┐   │
│  │ 账号与权限    │ │ Excel 导入   │ │ 报价查询/详情/追溯        │   │
│  └──────────────┘ └──────────────┘ └──────────────────────────┘   │
│  ┌──────────────┐ ┌──────────────────────────────────────────┐   │
│  │ 数据维护/审计 │ │ 备份与恢复（脚本+状态页）                  │   │
│  └──────────────┘ └──────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────────┘
   ↑                          ↑                          ↓
 授权用户浏览器            上游输入：xls/xlsx         输出：查询结果/导出(V1.1)
```

边界说明
- 本系统负责: 账号与 RBAC、Excel 解析/映射/预览/入库、结构化报价库、搜索/详情/追溯、纠错与软删除、审计日志、原文件与快照存储、备份脚本与状态展示
- 本系统不负责: ERP 流程、库存财务、与外部系统集成、域名/DNS/CDN 决策、微信抓取、AI 全自动导入
- 上游输入边界: 仅接受用户上传的 xls/xlsx 文件（限制扩展名、签名、大小），不接受系统间自动同步
- 下游输出边界: 页面查询结果、（V1.1）结构化 xlsx 导出；不对外提供开放 API
- 外部依赖边界: 仅 PostgreSQL（生产）与 SMTP/邮件通知均不强制；无其他外部服务依赖

### 1.7 名词术语表

- 术语: 导入批次（Import Batch）
  - 定义: 一次"上传→解析→确认入库"的完整事务单元
  - 在本系统中的含义: 报价/来源行的分组依据，批次内原子写入，失败整体回滚或明确标记部分成功
- 术语: 原始行快照（Source Row Snapshot）
  - 定义: 源 Excel 行的单元格级原文与定位（文件/表/行号/列名）
  - 在本系统中的含义: 不可覆盖的追溯事实源，结构化修正不改变快照
- 术语: 待核对（Needs Review）
  - 定义: 数据质量状态（PRD 7.5）
  - 在本系统中的含义: 低可信自动识别结果的标记，不阻塞查询但展示警告

### 2.3 约束条件

- 技术约束: PRD 8.4 推荐栈——Vue3 + TypeScript + Element Plus；Python + FastAPI；PostgreSQL；pandas/xlrd/openpyxl 或等效方案；Docker Compose 集中部署
- 组织约束: 小团队（1-2 研发），运维能力有限，禁止引入需要专职维护的中间件集群
- 时间约束: 无固定时间窗口，里程碑制
- 合规约束: 不公开注册；敏感信息最小化；审计留痕
- 成本约束: 单台云服务器 + 备份存储的最低成本形态

### 2.4 关键假设

假设 ASM-001
- 假设内容: 生产环境提供一台可安装 Docker 的 Linux 服务器与 HTTPS 入口
- 失效影响: 退化为 Windows 裸机部署（uvicorn + 反向代理），架构不变
- 验证方式: M5 前确认服务器与证书

假设 ASM-002
- 假设内容: 数据规模长期在 10 万条报价以内、并发 ≤ 50 用户
- 失效影响: LIKE 搜索与单机 PG 需重估（引入全文索引或只读副本）
- 验证方式: 每季度数据量盘点

假设 ASM-003
- 假设内容: 历史文件格式差异可被"标准模板自动识别 + 人工映射兜底"覆盖
- 失效影响: 人工映射工作量上升，不阻塞功能
- 验证方式: 样本扩容回归测试

## 3. 架构总览

### 3.1 架构原则

原则 1
- 名称: 可追溯优先
- 说明: 任何结构化数据必须能回到原始来源；原始快照只增不改
- 落地方式: 来源行快照表 + 文件存储；修正走修订记录；审计覆盖关键操作

原则 2
- 名称: 人工确认优先
- 说明: 不确定识别结果不静默入库
- 落地方式: 导入预览/校验/可信度标记；低可信记录状态=待核对；原文同存

原则 3
- 名称: 简单优先（规模适配）
- 说明: 5-10 用户、2 万条数据不引入搜索集群、消息队列、微服务
- 落地方式: 单体 FastAPI + 单库 + 同步导入事务；搜索用关系查询 + 索引

原则 4
- 名称: 最小权限
- 说明: 查询/维护/管理分权，敏感字段按角色最小化
- 落地方式: RBAC 三角色 + 后端逐接口鉴权 + 敏感字段脱敏与查看审计

## 4. 关键决策与权衡

### 4.1 技术选型总览

| 层次/能力 | 技术选型 | 版本 | 选型理由 | 备选方案 |
|-----------|----------|------|----------|----------|
| 前端 | Vue3 + TypeScript + Vite + Element Plus + Pinia + vue-router | Vue 3.5.x | PRD 8.4 推荐；B 端组件全 | React/Antd |
| 后端 | Python + FastAPI + SQLAlchemy 2 | Py3.12(容器)/3.14(本机) | PRD 8.4 推荐；异步性能与自动文档 | Django/Flask |
| 数据库 | PostgreSQL（生产）/ SQLite（本地开发方言兼容） | PG 15 | PRD 8.4 明确多人优先 PG | MySQL |
| Excel 解析 | xlrd 2.x（.xls）+ openpyxl（.xlsx），自研解析层 | 2.0.1 / 3.1.x | 纯 Python 依赖少，规避 pandas 在 Py3.14 的 wheel 风险；PRD 允许"或等效兼容方案" | pandas |
| 认证 | JWT（pyjwt）+ 服务端会话撤销表 + PBKDF2 哈希 | — | 退出/停用需即时失效，纯无状态 JWT 做不到 | cookie-session |
| 部署 | Docker Compose（nginx + backend + postgres + backup-cron） | — | PRD 8.4；单机低成本 | 裸机 systemd |
| 搜索 | PostgreSQL 关系查询 + B-tree/trigram 索引 + LIKE | — | 2 万条规模无需搜索引擎 | Elasticsearch（过重） |

### 4.2 关键决策（ADR 摘要）

ADR-001
- 决策主题: 单体架构而非微服务
- 背景: 5-10 用户、2 万条数据、1-2 名研发、无运维专职
- 已选方案: 单个 FastAPI 应用 + 单库 + 单机 Compose
- 备选方案: 前后端 + 独立导入服务 + 搜索服务（微服务）
- 主要权衡: 牺牲水平扩展与故障隔离，换取部署/运维/开发复杂度大幅下降；导入为同步事务保证批次原子性，避免引入任务队列
- 状态: 已采纳

ADR-002
- 决策主题: Excel 解析不依赖 pandas，直接使用 xlrd + openpyxl
- 背景: 本地开发环境 Python 3.14 的 pandas wheel 兼容风险；导入逻辑本质是"读行 → 映射 → 校验"，不需要向量化计算
- 已选方案: 自研 importers 解析层：xlrd 读 .xls、openpyxl 读 .xlsx，统一输出"单元格矩阵 + 类型信息"
- 备选方案: pandas.read_excel（PRD 提及的默认方案）
- 主要权衡: 多约 200 行自研代码，换取依赖树更小、Py3.14 兼容、单元格级控制（合并单元格/序列号日期/原文保留）更直接；PRD 8.4 明确允许"或等效兼容方案"
- 状态: 已采纳

ADR-003
- 决策主题: 双轨数据模型——结构化字段与原始快照并存，快照不可覆盖
- 背景: PRD 核心要求"清洗不等于删除原始信息"；争议时必须可核对
- 已选方案: 来源行快照表保存单元格原文与定位；报价等结构化表引用快照；修正写修订记录（前后值+原因+人+时间）
- 备选方案: 只存结构化字段 + 备份原文件（无法行级追溯）
- 主要权衡: 存储翻倍（可接受，2 万条级别），换取 100% 可追溯率
- 状态: 已采纳

ADR-004
- 决策主题: 认证采用 JWT + 服务端会话撤销，而非纯无状态 JWT
- 背景: FR01 要求停用账号立即失效、FR04 要求退出后令牌失效
- 已选方案: 短效 JWT（含 jti）+ 服务端会话表校验有效性；退出/停用即删会话记录
- 备选方案: 纯 JWT（无法即时失效）/ 纯服务端 Session
- 主要权衡: 每请求多一次会话表查询（可接受），换取即时失效能力
- 状态: 已采纳

ADR-005
- 决策主题: 本地开发用 SQLite，生产用 PostgreSQL，ORM 屏蔽方言
- 背景: 本机无 PostgreSQL/Docker；PRD 要求生产多人用 PG
- 已选方案: SQLAlchemy 2 声明式模型 + Alembic 迁移；连接串由环境变量决定
- 备选方案: 本机也装 PG
- 主要权衡: 方言差异（JSON 字段、ILIKE）需在代码中收敛为可移植写法；换取开发环境零门槛
- 状态: 已采纳（代码约束见 5.1 M-005）

ADR-006
- 决策主题: 横向多供应商拆分采用"列分组启发式 + 可信度标记 + 人工确认兜底"
- 背景: 样例 2 中"刘/曾/胡"等人名表头下挂多列（店名/电话/价格/备注），无法 100% 自动
- 已选方案: 尾部非标准列按"非空文本表头"分组为报价组；组内正则提取金额与渠道；提取成功→自动识别状态；存疑→待核对状态；整组原文进快照
- 备选方案: 全部交人工映射（工作量大）/ AI 提取（PRD 4.3 排除依赖 AI 100% 准确）
- 主要权衡: 识别规则非普适，靠状态标记与原文兜底保证"不错但可能不全"
- 状态: 已采纳

| 风险 | 可能性 | 影响程度 | 触发条件 | 缓解措施 | 负责人 |
|------|--------|----------|----------|----------|--------|

### 5.2 核心业务流程

流程 1：Excel 导入（最关键）

```text
维护员 → 前端上传向导 → /api/imports/upload（校验+存文件+扫描工作表）
      → /api/imports/preview（表头识别→映射建议→行级解析→拆分→重复标记→校验报告）
      → 用户确认映射/表头（可存映射模板）
      → /api/imports/commit（单事务: 物料/需求/供应商/报价/来源行 + 批次报告）
      → 前端展示成功/跳过/失败/待确认 + 行级原因
失败路径: 任意提交错误 → 事务回滚 → 批次标记失败 → 审计记录 → 无半批数据
```

流程 2：查询与追溯

```text
用户 → /api/quotes/search（关键词+筛选+排序分页）
    → 点击详情 /api/quotes/{id}（结构化字段+原始文本+文件/表/行号+批次）
    → （发现错误）维护员 PATCH /api/quotes/{id}（旧值留痕）
    → 修订记录 + 审计
```

流程 3：登录与权限

```text
用户 → POST /api/auth/login（限速）→ 校验 PBKDF2 哈希 → 签发 JWT(jti)
     → 服务端会话表登记
每请求 → Bearer Token → 校验签名+会话存在+用户启用 → RBAC 检查路由权限
退出/停用 → 删除会话记录 → 后续请求 401
```

### 5.3 失败、降级与补偿策略

场景 1：批次提交部分失败
- 失败表现: 写库中途异常（约束冲突/连接断开）
- 降级/兜底方案: 单事务整体回滚；批次标记 failed；错误详情返回
- 补偿方式: 用户修正后重新提交；文件与哈希保留可重试
- 用户影响: 无半批脏数据；需重新确认提交

场景 2：上传文件解析失败
- 失败表现: 加密/损坏/伪装扩展名
- 降级/兜底方案: 该文件标记失败并给原因，继续处理其余文件（FR05：单文件失败不影响其他文件）
- 补偿方式: 用户转换格式后重传
- 用户影响: 部分文件需人工处理

场景 3：搜索接口慢/超时
- 失败表现: P95 超标
- 降级/兜底方案: 强制分页上限；慢查询日志；必要时增加索引
- 补偿方式: 容量超 ASM-002 时引入全文索引方案（另行评审）
- 用户影响: 短暂变慢，不影响正确性

## 6. 数据架构

### 6.1 数据分类与生命周期

| 数据类型 | 示例 | 敏感级别 | 保存期限 | 销毁/归档策略 |
|----------|------|----------|----------|---------------|
| 主数据 | 用户/角色 | 中 | 长期 | 停用不删除 |
| 业务数据 | 物料/需求/供应商/报价 | 中（供应商联系方式高） | 长期 | 软删除保留可恢复 |
| 溯源数据 | 原始行快照/原文件 | 中（原文含敏感） | 长期（不可覆盖） | 随库备份 |
| 日志数据 | 审计记录 | 中 | ≥ 1 年（待确认） | 到期归档 |
| 会话数据 | 会话表 | 低 | 会话有效期 | 自动过期清理 |

### 6.2 数据流设计

```text
xls/xlsx 上传 → 文件校验/哈希/隔离存储 → 单元格矩阵 → 表头识别/映射
→ 清洗提取（价格/日期/含税含运）→ 横向拆分 → 重复检测 → 校验报告
→ 确认后事务入库（物料/需求/供应商/报价/来源行/批次）→ 索引 → 查询消费
```

### 6.3 数据存储策略

| 数据类型 | 存储介质 | 主责系统 | 保留策略 | 备份策略 |
|----------|----------|----------|----------|----------|
| 结构化业务数据 | PostgreSQL | M-005 | 长期 | 每日 pg_dump |
| 原始文件 | 文件卷 /data/uploads | M-006 | 长期 | 每日 tar 归档（与库同批次） |
| 备份产物 | 备份卷/异地（待定） | M-006 | 待确认（建议 30 天+异地） | 恢复演练验证 |

### 6.4 数据模型、一致性与状态边界

| 核心对象/数据域 | 主存储/事实来源 | 一致性要求 | 更新方式 | 备注 |
|----------------|-----------------|------------|----------|------|
| 物料/需求/供应商/报价 | PostgreSQL | 强一致（同批次单事务） | 同步 | 关系见 DB 设计 |
| 原始行快照 | PostgreSQL + 文件卷 | 强一致（随批次同事务） | 只增不改 | ADR-003 |
| 导入批次 | PostgreSQL | 强一致 | 同步 | 状态机: pending→confirmed→failed/partial |
| 会话 | PostgreSQL | 强一致 | 同步 | 撤销即时生效 |
| 审计 | PostgreSQL | 最终一致可接受 | 同步写 | 独立表，不可篡改约定 |

> 单体单库，无跨存储分布式一致性问题。

### 6.5 数据迁移、归档与回填

场景 1：模型变更
- 触发条件: 版本迭代修改表结构
- 方案: Alembic 迁移脚本，先备份后升级
- 回滚方式: downgrade 脚本 + 备份还原
- 风险: 大表加列锁表——2 万条级别可忽略

场景 2：映射规则升级后的存量数据
- 触发条件: 导入规则改进（如金额提取正则优化）
- 方案: MVP 不自动回填；提供按批次重新导入（新建记录）的人工路径；F-031 版本再议自动策略
- 回滚方式: 软删除误导入批次记录
- 风险: 重复记录——由业务疑似重复标记提示人工确认

## 7. 集成与接口架构

### 7.1 集成模式与交互边界

浏览器 SPA
- 交互模式: REST/JSON over HTTPS
- 交互介质/协议: HTTP 1.1，Content-Type application/json（上传 multipart）
- 方向: 单向客户端 → 服务端
- 说明: 无开放 API、无第三方系统集成

备份目标（运维侧）
- 交互模式: 脚本拉取/推送
- 交互介质/协议: 文件系统/可选 rsync
- 方向: 服务端 → 备份存储
- 说明: 异地副本位置待确认（PRD 10.3-10）

### 7.2 契约与版本管理策略

业务 API
- 契约形式: OpenAPI（FastAPI 自动生成）+ API 设计文档
- 版本策略: 路径前缀 /api/v1；破坏性变更升 /api/v2
- 幂等要求: 导入提交携带批次预览令牌防重复提交；其余写操作按业务键约束
- 错误模型: 统一 {code, message, details}；错误码见 API 设计文档

### 7.3 核心接口清单

| 接口/主题 | 方法/动作 | 用途 | 调用方/消费者 | 认证方式 |
|-----------|-----------|------|---------------|----------|
| /api/v1/auth/login | POST | 登录 | SPA | 无（限速） |
| /api/v1/auth/logout | POST | 退出 | SPA | Bearer |

## 8. 安全与合规

### 8.1 信任边界与威胁概览

| 边界/区域 | 主要资产 | 潜在威胁 | 控制措施 |
|-----------|----------|----------|----------|
| 终端到接入层 | 会话令牌、查询数据 | 窃听、暴力破解、越权 | HTTPS、登录限速、JWT 签名、RBAC |
| 服务到服务（容器网内） | API、DB | 容器逃逸（低） | 仅内部网络、DB 不映射公网端口 |
| 数据存储层 | 报价库、原文件（含手机号/账户） | 拖库、误删 | 最小化展示、审计、每日备份、恢复演练 |
| 上传通道 | 文件存储 | 恶意文件、路径穿越、伪装扩展名 | 签名校验（OLE2/ZIP）、大小限制、规范化文件名、不可执行目录、随机存储名 |

### 8.2 认证与授权

| 场景 | 认证方式 | 授权模型 | 会话/有效期策略 | 备注 |
|------|----------|----------|-----------------|------|
| 用户访问 | 账号密码 → JWT(jti) | RBAC 三角色（user/maintainer/admin） | 默认 12h 可配置；撤销表即时失效 | 不公开注册 |
| 服务间调用 | N/A（单体无服务间调用） | N/A | N/A | |

### 8.3 密钥与机密管理

| 机密类型 | 存储方式 | 轮换策略 | 访问控制 |
|----------|----------|----------|----------|
| JWT 签名密钥 | 环境变量（.env，不入库不入 git） | 可配置轮换（轮换后旧会话全失效） | 服务器运维 |
| 数据库密码 | 环境变量 | 待定 | 服务器运维 |
| 证书/私钥 | 主机文件挂载 | 按证书周期 | 服务器运维 |

### 8.4 数据保护与隐私

| 数据类型 | 保护措施 | 传输加密 | 存储加密 | 脱敏/最小化策略 |
|----------|----------|----------|----------|------------------|
| 密码 | PBKDF2-SHA256 高迭代 + 随机盐 | HTTPS | 不需（哈希） | 永不回显 |
| 供应商电话/地址/账户 | 角色限制（维护员/管理员）+ 查看审计 | HTTPS | 卷级（依赖主机） | 普通用户返回脱敏值 |
| 原始文件 | 随机存储名 + 不可执行目录 + 下载鉴权 | HTTPS | 卷级 | 按角色控制下载 |
| 查询结果 | 认证后响应 Cache-Control: no-store | HTTPS | — | 禁 CDN 缓存（Nginx 头） |

### 8.5 审计与合规

| 审计项 | 采集内容 | 保存期限 | 查询责任方 |
|--------|----------|----------|------------|

| 管理操作 | 用户启停/重置/角色变更 前后值 | ≥ 1 年 | 管理员 |
| 数据操作 | 导入批次/字段修正前后值+原因/软删除恢复/导出 | ≥ 1 年 | 管理员 |
| 敏感查看 | 谁/何时/查看了哪条记录的敏感字段 | ≥ 1 年 | 管理员 |

## 10. 性能与容量

### 10.1 负载模型

| 场景 | 峰值流量/规模 | 访问模式 | 数据增长预估 |
|------|---------------|----------|--------------|
| 读请求 | 10 并发、页面级 QPS < 50 | 搜索/详情 | 随查询习惯平稳 |
| 写请求 | 每日个位数批次导入 | 批量事务 | 2 万条起步，按文件增量 |
| 异步任务 | 每日 1 次备份 | cron | 备份体积随数据线性 |

### 10.2 性能目标

| 场景 | 指标 | 目标值 | 测试条件 |
|------|------|--------|----------|
| 关键词+筛选查询 | P95 | ≤ 2s | 2 万条报价、5 并发 |
| 详情接口 | P95 | ≤ 500ms | 同上 |
| 导入预览 | 总耗时 | ≤ 60s/1000 行 | 标准模板 |
| 首屏加载 | 静态资源 | gzip + 本地化 CDN 可选 | Nginx |

### 10.3 容量规划

| 组件 | 当前容量 | 目标容量 | 扩容方式 | 触发阈值 |
|------|----------|----------|----------|----------|
| PostgreSQL | 单机卷 | ≥ 50 万条报价 | 垂直扩容/升配 | ASM-002 失效 |
| uploads 卷 | 按 50GB 规划 | 可扩云盘 | 扩容挂载 | 磁盘 80% |
| 应用 | 单实例 | 单实例足够 | 垂直 | CPU 持续 > 80% |

### 10.4 性能优化策略

优化点 P-001
- 方案: 搜索字段（物料名称/编码/型号/品牌/供应商）建 B-tree + 可选 pg_trgm GIN 索引；查询强制分页与最大页大小
- 预期提升: 2 万条 LIKE 查询进入百毫秒级
- 验证方式: 基准脚本 + EXPLAIN

优化点 P-002
- 方案: 导入解析与校验在预览阶段完成并缓存行级结果，确认阶段纯写库单事务
- 预期提升: 确认秒级完成，避免超时
- 验证方式: 1000 行基准

### 10.5 性能测试计划

| 测试类型 | 工具 | 场景 | 通过标准 |
|----------|------|------|----------|
| 基准 | pytest + 时序断言 / httpx 脚本 | 三份样例导入 + 造数 2 万条搜索 | 10.2 目标值 |
